sidekick v0.8.0 runs embedding models on the CPU with ONNX Runtime, as well as on Core ML, so the same OpenAI-style API now works on Intel Macs and on Linux. Every release archive bundles its pinned runtime, which loads only when an ONNX model is installed. Six embedding models, exported once, grade A on this path on Apple silicon, Intel macOS and Linux x86-64. On Apple silicon, it gives a CPU path to check Core ML against.

## Upgrading

- **New archives.** Each release now ships four: `aarch64-apple-darwin` (as before), `x86_64-apple-darwin`, `x86_64-unknown-linux-gnu` and `aarch64-unknown-linux-gnu`. Each has `libonnxruntime.dylib` or `.so` beside `sidekickd`, with `ONNXRUNTIME_LICENSE` and `ONNXRUNTIME_THIRD_PARTY_NOTICES.txt`. When you upgrade in place, copy `libonnxruntime` along with `sidekickd`, or point `onnx_runtime` at a copy (below); otherwise a daemon with ONNX models reports the runtime unavailable and skips them. Core ML models are unaffected.
- **Platforms.**
  - Apple silicon: ONNX Runtime 1.28.3. sidekickd's minimum stays macOS 26.0.
  - Intel macOS: ONNX Runtime 1.23.2, the last Intel macOS build Microsoft published. It declares macOS 13.4, ONNX Runtime 1.23.2's own minimum, and is built and tested on macOS 26. Core ML runs on the CPU and GPU only (no Neural Engine): bge-small-en-v1.5's Core ML build grades A on both on a Xeon W-3235, and the parity suite skips the ANE path on a Mac without one. Core ML classifiers serve there too, with one caveat: Core ML's CPU path on Intel isn't bucket-invariant, so nlptown-sentiment's probabilities move by up to 1.9e-4 between buckets (its accuracy is otherwise A-level, worst Δp 7.35e-4). A classifier's default units run it on the CPU on an Intel Mac. Its GPU path grades A, and `[models."<id>"] compute_units = "cpu_and_gpu"` selects it. `/v1/chat` returns 503 (no Foundation Models).
  - Linux (glibc 2.35 or later): ONNX Runtime 1.28.3; ONNX models only, no Core ML or chat.
- **A new manifest backend, `backend = "onnx"`** (D40). It takes one `artifact = "<file>.onnx"` with dynamic shapes, and no buckets. Its parts:
  - `[io]` gains optional `token_type_ids` (fed zeros) and `position_ids` (fed 0..n); input integer types follow the graph.
  - `pooling` gains `"last_token"`.
  - A new `[onnx]` table has one key, `default_intra_op_threads`.
  - A 0.7.1 daemon skips a manifest with `backend = "onnx"` or `pooling = "last_token"` as unparseable, and serves the rest.
  - Existing Core ML manifests need no change.
- **New daemon config keys:**
  - `onnx_intra_op_threads` (all ONNX models);
  - `[models."<id>"] intra_op_threads` (one model);
  - `onnx_runtime = "<path to libonnxruntime>"`.
  
  A 0.7.1 daemon refuses to start with any of them, so keep that in mind if you share or roll back a config file.
- **New response fields, all additive:**
  - `/v1/models`: `backend` (`coreml`, `static` or `onnx`) on every embedder. ONNX models report `compute_units: "cpu"` and have no placement, `seq_cap` or `compute_units_source`.
  - `/health`: a new `onnx` object reporting the pinned and loaded runtime, where the runtime came from, thread settings and their sources, the detected cores, and which ONNX models are quantized.
  - Embedding responses from ONNX models: `sidekick-compute-units: cpu` and no `sidekick-buckets` header.
  - `sidekickd --version`: names the ONNX Runtime it expects.
- **Rust API changes.**
  - New variants `EmbeddingBackendKind::Onnx` and `Pooling::LastToken` break exhaustive matches on those enums.
  - Struct literals must add new fields: `ModelManifest { onnx, onnx_quantized }`, `CoremlIoNames { token_type_ids, position_ids }`, the server's `Config { onnx_intra_op_threads, onnx_runtime }`, `ModelConfig { intra_op_threads }` and `AppState { onnx_threads }`.
  - New items: `sidekick_core::onnx_graph`, `manifest::OnnxSection`, `sidekick_embed::{LoadOptions, load_embedder_with}`, and, behind the new `onnx` feature, `sidekick_embed::onnx` (`OnnxEmbedder`, `load_runtime`, `runtime_state`, `default_threads`, `detected_cores` and related constants).
  - Nothing was removed, and the `Embedder` trait is unchanged.
- **The C ABI is unchanged.** `libsidekick.dylib` is built without ONNX support: it skips ONNX manifests with that reason and never loads ONNX Runtime.

## ONNX Runtime on the CPU (D40)

An ONNX model is one graph with dynamic shapes, run by ONNX Runtime's CPU execution provider. sidekick tokenizes, prefixes, truncates and pools exactly as it does for Core ML, so the two backends differ only in the forward pass.

- **One input at a time, unpadded.** At a given thread count, a vector doesn't depend on what else is in the request or on re-runs; it's bit-identical. Batching and padding would move components by up to 2.6e-7, so sidekick doesn't batch.
- **int8 is detected and graded, not assumed.** ONNX Runtime's dynamic int8 kernels quantize activations with one scale per tensor over the whole batch. Their output then depends on batch-mates and padding, and on models with activation outliers the scale collapses. The registry marks graphs with quantization operators, and those always run alone. Qwen3-Embedding-0.6B in int8 (quantized from sidekick's fp32 export, or onnx-community's) grades **D** (worst cosine 0.40, on Apple silicon and Intel). The fp32 and fp16-weight builds grade A.
- **Checked at scan time, without loading the runtime:**
  - the graph's inputs, outputs and ranks against the manifest;
  - quantization;
  - external-data locations. A weights file outside the model's directory is refused, symlinks included. ONNX Runtime before 1.24 doesn't check this, and Intel macOS ships 1.23.2.
- **The runtime loads only when needed.** The daemon looks for ONNX Runtime only if an ONNX model is installed. It checks `onnx_runtime` in the config, then `ORT_DYLIB_PATH`, then the library beside `sidekickd`, and never searches system paths. Under launchd, which doesn't pass a shell's environment, use the config key or the bundled library.
- **Threads follow the hardware.** The default is the machine's fastest physical cores (performance cores on Apple silicon and hybrid Intel; physical cores otherwise, never SMT siblings), capped at 8. A manifest can raise its model's cap with `[onnx] default_intra_op_threads`. The operator's config always wins.

  Measured at about 290 tokens on four machines: 8 threads is within 21% of each machine's best for every model, and fastest outright on the M1 Max and the Ryzen 7 5800X. Running more threads than physical cores (SMT siblings) never clearly helps. On a Threadripper 3970X, 32 threads is no faster than 8 for long inputs and 3–4× slower for short ones. On the M1 Max, 10 threads (one per core, including the efficiency cores) is about 2× slower than 8. Qwen3-Embedding is the one model that keeps gaining past 8, by 17% at 16 threads on the Threadripper, so its manifest raises its cap to 16.

## Exporting and grading

- **`--format onnx` on the converters** exports a model's backbone with the same head and gate texts as its Core ML build. The graph outputs token-level `last_hidden_state`, which sidekick pools; a head that does more than pooling (EmbeddingGemma's) stays in the graph. `--onnx-weights fp16` halves the file and still computes in fp32. It saves disk, not memory: weights are upcast when loaded, and the process holds more than for fp32 (Qwen3-Embedding: +2.7 GB against +1.7 GB). There's no int8 export, for the reasons above.
- **The parity suite grades `onnx-cpu`** natively through the daemon's own code path. It builds with `--features onnx` alone and runs on Linux. It finds its fixtures with `--fixtures`, `SIDEKICK_FIXTURES` or `./fixtures`, so a copied binary works. `--external` grades vectors produced elsewhere as a cross-check. `onnx-cpu` floors are recorded for the M1 Max (ONNX Runtime 1.28.3) and the Xeon W-3235 (1.23.2); an int8 build fails them by design. The report's `macos` field now begins with "macOS ".

| model (sidekick's fp32 export) | M1 Max, 1.28.3 | Xeon W-3235, 1.23.2 | Ryzen 7 5800X, Linux, 1.28.3 | Threadripper 3970X, Linux, 1.28.3 |
|---|---|---|---|---|
| all-MiniLM-L6-v2 | A | A | A | A |
| bge-small-en-v1.5 | A | A | A | A |
| gte-modernbert-base | A | A | A | A |
| F2LLM-v2-160M | A | A | A | A |
| embeddinggemma-300m | A | A | A | A |
| Qwen3-Embedding-0.6B | A | A | A | A |

Every grade is at 1 − cos ≤ 2.4e-11 against fp32 sentence-transformers, over the parity suite's 51 inputs. The two Linux machines produce bit-identical vectors. The Core ML CPU path, by comparison, grades B on gte-modernbert, EmbeddingGemma and F2LLM. One more finding: onnx-community's published EmbeddingGemma fp32 export diverges past about 257 tokens (worst cosine 0.9936) because it doesn't halve the sliding window. sidekick's export matches transformers at every length.

## Choosing a CPU path on Apple silicon

`onnx-cpu` is the accurate CPU path, not the fast one. At 256 tokens, Core ML's fp16 CPU path is 3–5× faster; at 16 tokens `onnx-cpu` wins on four of five models, because Core ML pads to its smallest bucket. The Neural Engine and GPU are faster than both. `onnx-cpu` also holds its weights in process memory (+0.9 GB for gte-modernbert, +1.7 GB for Qwen3-Embedding fp32), where Core ML maps them from the file. The details are in [docs/MODELS.md](https://github.com/ironblock/sidekick/blob/v0.8.0/docs/MODELS.md).
