sidekick v0.6.0 turns two measured hardware limits into enforced caps with explicit opt-outs, reports where Core ML placed each bucket and which bucket answered each input, adds two zero-shot formats with Lumma-fev-0.1b (supported) and agent-jev (preview), and fixes idle unloading so a quiet daemon gives its memory back.

## Upgrading

- **Models over the Neural Engine's weight limit are now skipped** (D32). An ANE-served bucket (`compute_units` `cpu_and_ne` or `all`) with more than 1 GiB of weights isn't loaded, because Core ML would silently run it entirely on the CPU. `/health` and `sk_pool_skipped` give the reason and the fixes: serve it on the GPU (`compute_units = "cpu_and_gpu"`), reconvert with `--int8-embedding`, or opt out with `ane_weight_limit = "ignore"` in the manifest or `--ignore-ane-weight-cap` (`ignore_ane_weight_cap`) for the daemon. No model sidekick documents is affected.
- **CPU-served models are capped at 1,024 tokens** (D33). Past 1,024, Core ML's CPU fp16 matmul sums in a different order, so results depend slightly on the bucket. A model with `compute_units = "cpu_only"` doesn't load buckets above 1,024, and longer inputs follow the model's own over-length rules (a 400, or truncation where its format truncates). Opt out with `cpu_seq_limit = "ignore"` in the manifest or `--ignore-cpu-seq-cap` (`ignore_cpu_seq_cap`). Models served on the ANE, the GPU or `all` aren't capped.
- **Idle models are now unloaded on a timer.** `model_idle_ttl_secs` used to take effect only on the next request or `/health` call, so a daemon left alone kept every model loaded. Each pool now sweeps itself, and a model a request is still using is never unloaded: its idle time counts from when the last request finished.
- **New daemon config keys**, all off by default: `ignore_ane_weight_cap`, `ignore_cpu_seq_cap` and `report_compute_plans`.
- **Rust API: new public fields.** `Prepared` gains `decide_pos`, `seg` and `position_ids`. The manifest structs gain `ane_weight_limit`, `cpu_seq_limit`, `seq_cap`, `placement` and `fev`. New public items: `MAX_ANE_PROGRAM_WEIGHT_BYTES`, `AneWeightLimit`, `MAX_CPU_INVARIANT_SEQ`, `CpuSeqLimit`, `SeqCap`, `RecordedPlacement`, `RecordedPlan`, `FevSection` and `FevDelimiters`. Code that builds these structs with literals must add the new fields. The HTTP API only adds fields and a header, and the C ABI is unchanged.
- **Reconvert to get placement reporting.** Artifacts converted before this release keep working but report no placement.

## Where each bucket runs, and which bucket answered (D35)

- **`/v1/models` reports each bucket's placement**: Core ML's compute-plan op counts by device (`ane`, `gpu`, `cpu`). `/health` adds the unassigned ops, the names of the ops off the ANE, and where the counts were measured.
- **The counts come from conversion by default.** Converters record each bucket's compute plan in the installed manifest's `[placement]` table, stamped with the chip, the macOS build and the date. The daemon reports it as `source: "conversion"`, and marks it `stale` when the running chip or macOS build differs.
- **A live read is opt-in** (`report_compute_plans = true`). It's a second full compile per bucket: about 50 s for a 1,024-token bucket and nearly 4 minutes for a 2,048-token one on an M1 Max, plus disk and memory. Its counts report `source: "live"`.
- **A `sidekick-buckets` response header** lists the bucket each input used, in input order, on the classify, embeddings and rerank routes. Chat and static embedders omit it.

Placement is the compiled plan, not the device a particular prediction ran on, which Core ML doesn't expose.

## New models and formats

Graded by the parity suite against each model's ideal-fp16 ceiling, on an M1 Max with macOS 27. Bold marks the path each model is served on:

| model | format | served on | CPU | GPU | Neural Engine |
|---|---|---|---|---|---|
| Lumma-fev-0.1b | fev (new, D34) | ANE | D, with the D33 limit past 1,024 tokens | A (0.95× ceiling) | **B** (1.57× ceiling, no flips) |
| agent-jev, **preview** | agentjev (new, D36) | GPU | F (bucket invariance) | **A** (0.70× ceiling, no flips) | F (over the weight limit, it runs on the CPU) |

- **Lumma-fev-0.1b** (FrontiersMind, 154M parameters) reads the request's state and one question in one row, and scores each option against a final decide token. It's supported: it passes every gate and is exactly bucket-invariant on the ANE. Requests take about 33 ms at 256 tokens and about 1.2 s at 2,048. Its gold accuracy on fast-decisions (30.7%) matches fp32.
- **agent-jev** (598M parameters, Qwen3-0.6B) scores a question's candidate answers as a set. sidekick lays the question out once as a tree, a shared prefix and then each candidate's branch, which reproduces the authors' per-candidate scoring in one pass to |Δp| 5e-7 in fp32. It's served on the GPU, because its 1.12 GiB of weights exceed the ANE's limit. It stays a preview: its CPU path depends on the bucket even below 1,024 tokens, which isn't explained yet. Its authors report modest quality (AUROC 0.589 for coding-task completion, where 0.5 is chance), and sidekick grades fidelity only.
- **Parity, not accuracy.** Each model is graded against its own fp32 output.

## Grading and conversion tools

- **`--int8-embedding`** stores only a model's token table (a CPU-side lookup) as per-row int8. It's the first weight quantization, the way to bring a model just over the ANE's weight limit under it, and it's graded against the ideal-fp16 ceiling like any other rewrite. Chunked variants, which lose no precision, are planned.
- **Converters enforce the ANE weight limit** for ANE-served artifacts, and name the fixes. `--ignore-ane-weight-cap` builds anyway, with a warning per bucket and a note in the report and the installed manifest.
- **The parity suite reports the CPU's past-1,024 bucket check as the D33 limit** with its measured variation, rather than failing it. It treats a compute plan as a gate only for ANE-served models, and samples bucket invariance for buckets over 512 tokens (D26 amendment).
- **Fixed: bogus ideal-fp16 ceilings for hand-written RMSNorm.** The fp16 simulator rounded each step of an RMSNorm written out by hand (Qwen3, Gemma, Llama), where x² overflows fp16 and silently zeroed tokens with large activations. A normalization is now one operation, and an overflow anywhere it isn't handled exactly raises `Fp16Overflow`. Ceilings for models using PyTorch's LayerNorm don't change.
- **New repro:** `tools/repro_cpu_matmul_accumulation.py` shows the CPU matmul's change of summation order past 1,024.

## Memory

The README has a new Memory section, measured on an M1 Max with macOS 27:
- On the ANE, sidekickd's own footprint stays small (57–200 MB). Weights are read through the reclaimable file cache, and the ANE pins part of them (about 0.8 GB for laya-typed-decisions), released on unload.
- On the GPU, the weights are mapped into sidekickd: about a bucket's weight size per loaded bucket.
- A bucket's first load compiles it, briefly costing memory in Apple's ANE compiler service (up to 1.3 GB) and disk for the compiled bundle.
