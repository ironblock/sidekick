sidekick v0.7.0 is about running a small model beside a larger one. A bucket can now be a chain of Core ML programs, each under the Neural Engine's weight limit, so a model over 1 GiB can run on the ANE. The operator, not only the manifest, chooses where each model runs. Measured beside a 27B model on the GPU, that choice decides whether the larger model stays loaded.

## Upgrading

- **Chunked models need this release** (D37). Converters now split a model over 0.9 GiB of weights per bucket into chunks by default, for backbones that can be chunked (today agent-jev's Qwen3); `--chunks 1` keeps one program per bucket. A 0.6 daemon lists a chunked model but fails every request to it, naming the missing artifact, so it never serves part of one. Models under the budget convert exactly as before.
- **New daemon config table** (D38): `[models."<id>"] compute_units = "cpu_and_ne"` (or `cpu_and_gpu`, `cpu_only`, `all`) serves that model on other compute units than its manifest names. A 0.6 daemon refuses to start with a config that has a `[models]` table, since its config rejects unknown keys.
- **New response fields, all additive:** `compute_units_source` (`manifest` or `operator`) in `/v1/models`; `compute_unit_overrides` and `chunked_models` in `/health`. The `sidekick-compute-units` header keeps its meaning: the units the model runs on.
- **Rust API changes.**
  - `BucketModels::new` takes a chunk count, and `BucketModels::get` returns an `Arc<CoremlChain>`.
  - `ane_weight_refusal` takes a chunk count.
  - `artifact_path_for_bucket` is removed; use `artifact_paths_for_bucket`, which returns one path per chunk.
  - The manifest structs gain `chunking` and `compute_units_source`, `ScanOptions` gains `compute_units`, and `RecordedPlacement` gains `alternatives`, so code building these with literals must add them.
  - New public items: `BucketModels::units` and `BucketModels::resident`, `CoremlChain`, `Chunking`, `ComputeUnitsSource`, `AlternativePlacement`, `artifact_files`, `CHUNK_HIDDEN_IN`/`CHUNK_HIDDEN_OUT`, and `ModelRegistry::unmatched_overrides`.
  - The C ABI is unchanged; `libsidekick.dylib` reads no daemon config, so it keeps the manifests' compute units.
- **A loaded model keeps no bucket resident until a request uses it.** Loading still checks every bucket, so a broken artifact fails the load as before, but the smallest bucket is no longer kept loaded for the check. A model's first request loads its bucket; a live compute-plan read (`report_compute_plans`) follows that load. `compute_units()` on a Core ML classifier or embedder now reports the units sidekick configures, without loading anything.
- **Placement records for both unit sets.** Converters record the compute plan for `cpu_and_ne` and `cpu_and_gpu` (`[placement.alternatives.<units>]`), so a model the operator moves keeps its placement report. A 0.6 daemon ignores the extra table.

## Chunked buckets (D37)

Core ML runs a program on the Neural Engine only if its weights are under about 1 GiB (D32), but the limit is per program. The converter now splits a bucket in torch at layer boundaries before tracing, so only the fp16 residual stream crosses from one chunk to the next, and each chunk keeps every sidekick rewrite. The daemon runs a bucket's chunks in sequence, loads them all or none, and checks the weight limit per chunk.

- **The boundary loses nothing.** On the GPU, chunked agent-jev's output is bit-identical to the unchunked model's, at under 2% more latency; the converter checks that bit-identity in the smallest bucket of every chunked conversion.
- **agent-jev, chunked** (1.115 GiB, two chunks of 0.57 GiB; 2,627 cases, M1 Max, macOS 27): GPU **A** (0.85× its ideal-fp16 ceiling, unchanged), CPU D, and the Neural Engine **D** (4.2× the ceiling, no decision flips, buckets exact, 98–99% of operations on the ANE). Why the Neural Engine's fidelity is lower is #48. agent-jev stays served on the GPU by default; the Neural Engine is an option.
- **One artifact serves either placement**, so moving a model between the GPU and the Neural Engine is a config change, not a reconversion.

## Choosing where a model runs (D38)

The daemon config can now set a Core ML model's compute units by id. The weight limit (D32) and the CPU length cap (D33) judge the operator's choice exactly as they judge the manifest's, and a refusal names the override. `/v1/models` and `/health` say who chose.

## A companion beside a larger model

Measured on a 32 GB M1 Max with macOS 27: chunked agent-jev answering one 1,024-token request a second, beside a 4-bit 27B Qwen3.8 that oMLX serves on the GPU with speculative decoding. The same install was switched between placements with D38.

| companion on | sidekickd memory | the 27B | the companion, alone (median, power) |
|---|---|---|---|
| GPU | 1,195 MB | unloaded within seconds by oMLX's memory-pressure policy; no generation completed | 226 ms, 7.4 W |
| Neural Engine | 58 MB | every generation completed, about 2% below its decode rate alone | 377 ms, about 1.9 W |

On the GPU, Core ML maps a model's weights into sidekickd; on the Neural Engine they're read through the reclaimable file cache. The eviction is oMLX's own policy on a machine this size, not a general property of the GPU. The harness is `tools/companion_bench.py`, and the details are in D37 and [docs/MODELS.md](https://github.com/ironblock/sidekick/blob/v0.7.0/docs/MODELS.md).

## Fixes

- **A model no longer keeps its smallest bucket resident.** It was loaded at startup to validate the model, and stayed. For chunked agent-jev served on the GPU, answering 1,024-token requests, sidekickd's resident memory falls from 2.4 GB to 1.3 GB, and the first request is faster (1.0 s, was 1.3 s), since it no longer loads the smallest bucket as well. The companion measurement above used a 1,024-only install, so it isn't affected.

- **Reading a compute plan could abort the daemon.** With `report_compute_plans = true`, a model removed or reinstalled after its load made Core ML abort sidekickd with an uncaught exception during the background plan read. sidekick now checks the artifact is still there before asking Core ML, which narrows the window to the read itself.
- **Conversions no longer leave Core ML cache behind.** Core ML kept a compiled-bundle cache entry for every bucket a converter moved into place, about 11 GB for a large model. Converters now run with a private cache that's removed when they exit.
